# vue-quasar

Quasar building the bake-off screen in Vue 3.

Read [`spec/screen-spec.md`](../../spec/screen-spec.md) before writing code. Sections 2 to 9 are the requirements. A requirement this library cannot meet is recorded as a failure, not worked around.

```
pnpm --filter @bakeoff/vue-quasar dev
pnpm --filter @bakeoff/vue-quasar test
pnpm --filter @bakeoff/vue-quasar build
pnpm --filter @bakeoff/vue-quasar measure
```

Write only inside this folder and `results/vue-quasar.json`. `packages/criteria` and `packages/harness` belong to the phase one owner.

## Notes for the write-up

**Result: 18/18 criteria pass.** Bundle: 115.84 KB total gzipped, 24.21 KB baseline, 91.63 KB delta, within the 180 KB budget.

### What Quasar gave for free

- `QDialog`: `role="dialog"`, `aria-modal="true"`, a real focus trap, initial focus on the field marked `autofocus`, and focus return to the triggering row on close. Two `QDialog`s stack correctly (the record modal and the unsaved-changes confirmation), same as Headless UI's `Dialog` did for `react-headless`. None of this is hand-written. One caveat: `persistent` (needed so Escape does not silently discard the form) also suppresses Quasar's own `escape-key` event, so this build listens for the native `keydown` itself on the dialog's content rather than relying on that event — a small, working workaround, not a gap.
- `QSelect`: the entire dropdown UI (trigger, popup, `role="option"` items, `aria-selected`, keyboard navigation, multi-select chips-or-summary behaviour) came from the library, for both the filter form's multi-selects (Status, Priority) and every single-select (Assignee, and the modal's Status/Priority/Assignee). Nothing about the select's own UI is hand built, a real difference from `react-headless`, whose Headless UI `Listbox` needed a hand-built trigger summary and checkmarks on top of the library's behaviour.
- `QInput`: label association (`<label for>`), placeholder, and error display (`.q-field__messages`) all came from the component; the validation logic that decides *when* to show an error is this build's own.
- `QBadge`, `QSkeleton`, `QBtn`: used for the status/priority badges, the loading skeleton bars, and every button in the screen (sort headers, pagination, Save/Cancel/Retry/Clear). All real Quasar components, not just styled to look like them.
- The Vite plugin (`@quasar/vite-plugin`) auto-imports and registers whichever `<q-*>` tags a template uses, so application code never writes a `quasar` import for a component. `libraryImports` in the measured ergonomics is 1 (the `app.use(Quasar, ...)` call in `main.ts`) precisely because of this.

### What had to be hand built

- The entire table: semantics (`caption`, `scope`, `aria-sort`), the three-state sort cycle (ascending, descending, back to the default `updatedAt` descending), client-side pagination with First/Previous/Next/Last, the `Showing X to Y of Z` live region, and the row-as-a-control keyboard handling (Enter/Space open the modal). Quasar ships `QTable`, and it does support a comparable three-state sort toggle (`binary-state-sort` off), but wiring its internal sort/pagination model to this spec's exact default-column behaviour and First/Last controls would have meant overriding most of what `QTable` does internally. Given the time available, this build hand-rolled the table instead of fighting that override, the same call `react-headless` made for the whole table since Headless UI ships no table primitive at all — the difference here is that Quasar could plausibly have carried more of this with more integration effort, so this is a build choice as much as a hard capability gap.
- The toast system in full: the stack, the cap of 3 with oldest-dropped-first, the 4s/3s auto-dismiss timers, dismiss-by-button and dismiss-by-Escape, and an `aria-live="polite"` region mounted before the first toast ever fires. Quasar ships `$q.notify()`, which handles the visual side of a toast well, but its documentation does not commit to a pre-mounted live region, an Escape-to-dismiss binding, or a hard stacking cap — reproducing all three exactly would have meant overriding most of what the plugin does. This build hand-built the toast store instead, the same conclusion `react-headless` reached for a library with no toast primitive whatsoever, though Quasar at least has one to start from.
- Status/priority badge styling, date formatting (`MMM d, yyyy`, UTC-normalized), and the relative-time formatter for `updatedAt`, same as every other build in this comparison.
- All validation, touched-tracking, and the unsaved-changes confirmation flow around the modal. The dialog mechanics are free; the form behaviour is not, and never is, regardless of library.

### Accessibility (section 9)

Declared `requirementsNeedingCustomCode: 6` in `bakeoff.json`, the same count and the same six code-relevant bullets `react-headless` used (semantic HTML/ARIA, keyboard + focus-visible, tab order, table semantics, aria-sort/live regions, zero axe violations) for comparability. Every one of the six still needed some hand-written work here too, but for a narrower reason than for an assembly kit: the parts of the screen this build chose to hand-build (the table, the toasts) touch nearly all six bullets by themselves, while the parts that came from Quasar (the dialog, the selects, the inputs) arrived with correct semantics, keyboard support, and focus handling already in place. A build that used `QTable` and `$q.notify` more aggressively could plausibly report a lower number; this one traded that for certainty about matching the spec's exact behaviour.

`axeViolationsBeforeFixes: 1` — the first real run against the loaded table and the open modal (criteria 17 and 18) reported one violation: a critical `label` rule with 2 affected nodes. The cause was this build's own markup, not a Quasar default: the Created-range date fields were wrapped in a hand-written `<label>From ...</label>` / `<label>To ...</label>`, and `QInput` already renders its own `<label for="...">` internally when given a `label` prop, so the result was two nested `<label>` elements pointing at the same input. Removing the outer wrapper and passing `label="From"` / `label="To"` to `QInput` directly (matching how the Search field was already written) cleared the violation. Worth flagging for whoever else builds with Quasar: a component that already renders its own `<label>` makes wrapping it in another one an easy, silent-until-axe mistake. As with every build in this comparison, axe runs here under jsdom, which has no real layout or canvas (`HTMLCanvasElement.getContext` is not implemented), so axe's `color-contrast` check throws internally and cannot evaluate real contrast in this environment; "zero violations" reflects everything axe can check under jsdom, not a substitute for the manual NVDA/VoiceOver pass or a browser-based axe run.

### Adapter notes

- `FilterProbe.values()` and the multi-select readbacks use a visually-hidden mirror span next to each filter field (see `FilterForm.vue`), the same technique `react-headless` used for Headless UI's `Listbox`, because the interface requires a synchronous read and opening a `QSelect` popup to inspect `aria-selected` is asynchronous.
- Closing a `QSelect` popup from the adapter uses `mousedown`/`mouseup` on `document.body` rather than a synthetic `click` or an Escape keydown: Quasar's outside-press detection listens for `mousedown`, and neither a bare `click` event nor Escape (tried first) actually closed the popup under jsdom. This is a real, working control interaction, not a shortcut around one.
- No adapter method had to throw. Nothing in the 18 criteria exposed a gap Quasar could not be made to do, though the table and the toasts needed real construction rather than assembly, as detailed above.

### Tooling snags (not part of the 18, but worth recording for the phase one owner and later builders)

- `packages/criteria/jest-preset.json`'s `transform` key is the literal string `"^.+\.(t|j)sx?$"`; `\.` is not a legal JSON escape, so `JSON.parse` throws on that file outright, the same bug `react-headless` already filed. Worked around the same way: the settings are inlined, correctly escaped, in this build's own `jest.config.js`.
- The scaffolded `package.json` test script pointed at `../../node_modules/jest/bin/jest.js`, which this pnpm workspace does not hoist. Pointed it at `node_modules/jest/bin/jest.js` instead, same fix `react-headless` made. Its `--experimental-vm-modules` flag also had to come off: this build runs Jest's classic CommonJS pipeline throughout (see below), and that flag reintroduces native ESM handling for `.js` files under a `"type": "module"` package regardless of the rest of the config, which broke the Quasar client-build transform below all over again.
- Nothing writes `criteria-results.json` on its own (`handoff.md` section 6); added the same small local Jest reporter pattern `react-headless` used (`test/reporter.cjs`), adapted for this build.
- Getting Vue, Quasar, and Jest's ESM-vs-CommonJS handling to agree took real trial and error, worth recording since the other two Vue builds will hit the same shared-tooling edges:
  - Jest's `jsdom` test environment defaults to the `"browser"` export condition. Vue's package `exports` map has no `"browser"` entry, so resolution fell through to the `esm-bundler` build (meant for further bundling, not direct execution) and failed to parse. Fixed with `testEnvironmentOptions: { customExportConditions: ['node', 'node-addons'] }`, which makes Jest pick Vue's Node-targeted build instead.
  - `@vue/vue3-jest` compiles `.vue` files to CommonJS `require()`/`exports` regardless of Jest's own ESM settings. Running Jest in its native ESM mode (`--experimental-vm-modules`, `extensionsToTreatAsEsm`) alongside that produced unresolvable `ERR_REQUIRE_ESM` / "does not provide an export named 'default'" failures once a `.vue` file's compiled output reached `@bakeoff/fixture` (an ESM-only workspace package) or one of this build's own composables. The fix was to run Jest's classic CommonJS pipeline throughout instead (drop `--experimental-vm-modules` and `extensionsToTreatAsEsm`) and let `ts-jest`'s default CommonJS output match `vue3-jest`'s. `ts-jest` still transpiles `@bakeoff/fixture`'s TypeScript source (its real path resolves outside `node_modules` through the pnpm symlink, so the default `transformIgnorePatterns` does not exempt it), so the workspace package's `import`/`export`/dynamic `import()` never reach Jest as raw ESM in the first place.
  - Quasar's bare `quasar` specifier resolves, under a CommonJS `require`, to an SSR server build (`quasar.server.prod.cjs`) that throws without an `ssrContext` outside actual SSR. The real client build (`quasar/dist/quasar.client.js`) only ships as ESM source. Fixed by adding a `moduleNameMapper` alias to the client build plus a scoped `transform`/`transformIgnorePatterns` entry that runs that one file through `ts-jest` (with `allowJs: true`) to convert it to CommonJS, rather than requiring it raw.
  - `@quasar/vite-plugin`'s auto-import-and-register transform only runs inside Vite, not inside `vue3-jest`, so the Jest environment registers the handful of Quasar components this screen uses by hand (`Quasar, { components: { QBtn, QInput, QSelect, QDialog, QCard, QCardSection, QCardActions, QBadge, QSkeleton } }`) in `test/adapter.ts`'s `mount()`. This does not change what ships in the production bundle, which still relies entirely on the Vite plugin's auto-import.
  - jsdom implements neither `Element.prototype.scrollTo`/`scrollIntoView`, `ResizeObserver`, nor `window.matchMedia`, all of which Quasar's components touch internally (`QBtn`'s focus/ripple handling, `QSelect`'s virtual scroll, the platform/screen plugin). No-op polyfills for all four live in `test/setup.ts`.
  - Quasar's dialogs move focus (on open) and return it (on close) only after their show/hide transition settles, which takes the full `transition-duration` (default 300ms) even though jsdom has no real CSS transitions. `table.pressEnterOnRow()` polls (`waitFor`) until focus actually lands inside the dialog rather than assuming a fixed delay, which is also more robust than a hard-coded sleep against a slower CI machine.
- One real application bug caught by this process, not a tooling one: `useFilters.ts`'s page-reset watcher originally ported React's `useEffect`-plus-`firstRun`-ref pattern from `react-headless` verbatim. Vue's `watch()` (without `immediate: true`) never fires on initial setup the way React's `useEffect` always fires once on mount, so the ported `firstRun` guard was silently swallowing the *first* real filter change's page reset. Criterion 9 caught it directly; the fix was to delete the guard, since every firing of a non-immediate Vue watcher is already a genuine subsequent change.
