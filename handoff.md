# Handoff: UI library comparison

**Updated:** 2026-09-03

## 1. What this is

The workspace behind `bakeoff-screen-spec.md`, which lives in `../demo-resume/` and is copied here as `spec/screen-spec.md`. Eight UI libraries build the same `/tickets` screen so they can be compared on ergonomics, bundle size, and accessibility defaults.

Demo content. The domain, the data, and the numbers are fictional, matching `../demo-resume/demo-resume.md`. Git history starts at the phase one commit, which is the baseline every build diffs against.

Phase one is built and frozen. Phase two, the eight builds, is done: all eight of `builds/` are built and scored, and `results/` has all eight files. Every build passes all 18 criteria; `react-antd` passes all 18 but is over the 180 KB bundle budget. All eight builds are committed, one commit each, on top of a lockfile commit. On 2026-09-03 all eight dev servers were started at once and served their screens, verifying only that each app boots; nobody has clicked through the eight screens in a browser yet.

## 3. The rules that govern edits

Phase one is the fixed input. Nobody working on a build edits `packages/criteria` or `packages/harness`. A criterion that looks wrong goes back to the phase one owner as a question, because a test patched locally ends the comparison and CI will not say so. The `builds` job diffs both packages against main for exactly this.

The slice is one library, never one feature. A feature slice would put eight workers inside the same eight folders. A worker writes only inside its own `builds/<name>/` and its own `results/<name>.json`.

`tickets.json` is committed and the seed is fixed. CI regenerates it and fails on a diff. If it ever changes, every earlier bundle and render number stops comparing and the run starts over.

Run `pnpm fixture:check` after touching the fixture. The criteria assume a row on each Created boundary, a search matching exactly one row, subjects spanning A to Z, and a status and priority pair with rows. That script asserts all of it.

A library that cannot meet a requirement records the failure. Do not bend the spec, and do not return a plausible fake from an adapter method to get the suite green. Throw instead. A thrown criterion is a recorded result.

## 4. Decisions made

- The fixture loads through a dynamic import inside `loadTickets`, so a bundler emits the 240 rows as their own chunk. Section 10 excludes the fixture from the size total, and `measure` can only do that if the rows are not inlined. A static import of `@uilc/fixture/data` in application code folds them back in and inflates the number. Tests import the static entry point freely.
- The generator is not re-exported from `@uilc/fixture`. It reads and writes files, and re-exporting it dragged `node:fs` into the browser bundle and broke `vite build`. It has its own entry point.
- `measure` reads the bundle and the ergonomics counts off the code. The two things a script cannot see, how many section 9 requirements needed custom code and whether the modal, select, and toast were hand built, come from a `comparison.json` each build declares.
- Lighthouse needs a served build and a browser, so a local `measure` writes `runs: 0` rather than inventing a number. CI supplies the median.
- A build with no `criteria-results.json` scores as 18 failures, not as 0 passes and 0 failures. A missing test run must never read as a clean one.
- The template splits into `common` plus a `react` or `vue` overlay. The two differ in the entry file, the Vite plugin, the dependencies, and a `.vue` type shim, and nothing else. A scaffolded build typechecks, builds, and measures before anyone writes a line.
- Each build's Vite config matches its baseline: no manual chunking, no external-ing the library. Either would move weight out of the number the comparison is about.
- The roster lives in `scripts/roster.ts` rather than inside the scaffold, because importing it from `new-build.ts` ran that script's CLI as a side effect.
- Each build pins its own dev server port in `vite.config.ts` under `server`, 5173 through 5180 in roster order (`react-headless` 5173, `react-shadcn` 5174, `react-mui` 5175, `react-chakra` 5176, `react-antd` 5177, `vue-vuetify` 5178, `vue-primevue` 5179, `vue-quasar` 5180), with `strictPort: true` so a collision fails loudly instead of silently landing on another build's screen. All eight can then run at once for side by side comparison. This only touches `server`, never `build`, so the bundle numbers are unaffected and the configs still match their baselines.

## 5. Gotchas

- Scaffolding a build needs `pnpm install` afterwards, or its workspace dependencies are not linked and everything reports as missing modules.
- `measure` identifies the fixture chunk by basename, matching `tickets-*.js` or `data-*.js`. A bundler that names chunks differently needs that regex updated, or the fixture counts against the budget.
- The criteria compare against `expected.ts` rather than against numbers typed by hand, so regenerating the fixture does not silently invalidate the suite. Keep it that way.
- `pnpm typecheck` covers the three shared packages only. A build typechecks through its own `tsconfig.json`.
- Files are written with LF newlines. Preserve that.
- The user's writing rules ban em dashes and a list of marketing words. Every markdown file here has none. Keep new prose in the same register.
- `packages/criteria/jest-preset.json` is invalid JSON: the pattern `"^.+\.(t|j)sx?$"` uses `\.`, which is not a legal JSON escape, so `JSON.parse` throws on it. Every build hits this. `react-headless` worked around it by inlining the same, correctly escaped settings directly in its own `jest.config.js` rather than touching the shared file. This is a phase one bug and belongs to the owner, not to per-build workarounds.
- The scaffolded test script assumes a hoisted `jest` binary (`../../node_modules/jest/bin/jest.js`), which does not match this pnpm workspace's layout. `react-headless` pointed its script at its own `node_modules/jest/bin/jest.js` instead.
- axe-core under jsdom cannot check color contrast (`HTMLCanvasElement.getContext` is not implemented in jsdom), which logs a harmless console error during the axe criteria. A "zero violations" result is real for what axe can evaluate under jsdom, but is not a substitute for a manual screen-reader pass or a browser-based axe run.
- Under Jest's `--experimental-vm-modules`, a default import from a CJS library subpath (e.g. `import Button from '@mui/material/Button'`) can resolve to the whole module object instead of the component, because Node's native CJS-to-ESM interop binds the default import to `module.exports` wholesale rather than `.default`. `react-mui` hit this and fixed it by switching to named imports from the library's barrel (`import { Button } from '@mui/material'`) in both app and test code. Watch for it in any build pulling components from CJS subpaths; it does not affect the Vite production build, only Jest.
- `react-chakra`'s Ark UI dialog/toast state machines schedule some updates on `requestAnimationFrame`, so its adapter waits for focus to actually land or return rather than for the element to appear or disappear. Its `createToaster()` is a module-level singleton that survives Jest's mount/unmount cycles, so its adapter calls `toaster.remove()` in `unmount()` to stop bleed between tests.
- `measure`'s "library imports" ergonomics count only sees explicit `import` statements. `vue-vuetify` (and, the same way, any Vue-suite build using `vite-plugin-vuetify`/`unplugin-vue-components`-style auto-import, likely `vue-primevue` and `vue-quasar` too) resolves `<v-btn>`, `<v-select>`, etc. from template tags at build time, so the count undercounts real library usage for those builds. This is a `measure`/phase one limitation, not a build bug; flagged for the owner rather than worked around.
- `vue-primevue`'s Jest setup needed more than the two react-headless workarounds: `@vue/vue3-jest` always downlevels a `.vue` file's compiled template to CommonJS via Babel regardless of Jest's ESM settings, and PrimeVue ships ESM-only with no `require` fallback, so the build runs Jest in CommonJS mode with a widened `transformIgnorePatterns` (documented in its `jest.config.js`). `@primevue/themes`'s `aura/<name>` subpaths are also import-only with no CJS fallback; worked around by depending on `@primeuix/themes` directly, which the `@primevue/themes` package itself re-exports from.
- PrimeVue's single-value `Select` commits an option on `mousedown`, while its `MultiSelect` sibling commits on `click`, so a one-size-fits-all "click the option" test helper silently no-ops on `Select`. Its `MultiSelect` combobox is also a visually hidden `<input>` whose own click handler ignores clicks on itself, so a test has to click its `[data-pc-section="root"]` ancestor, not the element `getByRole('combobox')` naturally returns.
- Killing a backgrounded `pnpm dev` from the agent harness on Windows stops the wrapper shell but leaves the child `vite` process holding the port, so the next start fails with "Port 5173 is already in use". Find the owner with `netstat -ano | grep ':5173'` and `taskkill //PID <pid> //F`.
- The Puppeteer MCP server drives ONE shared browser instance across every agent in a session. Running several agents that each navigate it at once makes them race: an agent screenshots and gets another build's screen back. Verify visually one agent at a time, or have each agent confirm `document.title` in the same call as the measurement it takes.
- A builder agent told to run the criteria suite will sometimes background its own test run, end its turn saying it will "report back when the notification arrives", and then wait forever, because nothing wakes it. Three of the eight builds did this. Tell builders to run the suite in the foreground, and if one returns a status message instead of results, message it back rather than assuming it failed.
- `axe-core` runs 2 to 4 real minutes per test against a heavier DOM (Ant Design's `rc-table` virtual-list scaffolding, `rc-select`'s duplicated option lists), and chained `Select` interactions in `react-antd`'s filter criteria pass Jest's 15 second default. Its `jest.config.js` raises `testTimeout` to 300000ms; this does not loosen any assertion, it only stops correct-but-slow interactions from racing the clock. Worth checking if it recurs on other suite-kind builds.

## 7. UI defects found and fixed on 2026-09-03

A first pass over all eight screens at 1440px wide, first paint only. Nobody has opened a modal, fired a toast, paged, or checked a narrow viewport yet, so this was the visible surface of the default state and not a full audit. All eight are fixed, one agent per build, each confirming its own 18 criteria still pass and re-measuring its own bundle. None of it is committed.

Two rules governed every fix. Differences in look between libraries are the finding the comparison exists to record, so a fix corrects something broken inside one build and never restyles a build to resemble another. And every fix re-runs `pnpm --filter @uilc/<name> test`, plus `measure` if it touched anything that lands in the bundle.

The pattern worth carrying forward: seven of the eight were a single missing or wrong line of setup, not accumulated sloppiness. Three builds were not loading something the library assumed (Vuetify's base stylesheet, an icon glyph, Chakra's width cap), and one was inheriting a default nobody chose (PrimeVue's system dark mode). Look for the one-line cause before writing CSS to cover a symptom.

- `react-headless` (5173): the `<legend>` of the Created between `<fieldset>` sat outside the flex flow and stretched the filter row, leaving a band of empty space above the other fields. Fixed by making the fieldset a plain block with a flexed inner wrapper and inline From and To labels. Bundle 89.73 to 89.76 KB total, 44.85 KB delta.
- `react-shadcn` (5174): the page container was `max-w-5xl`, about 150px too narrow for the filter row, so Created between and the Clear filters group wrapped to a second line under dead space. Widened to `max-w-7xl`. The Assignee caret was a literal `▾` character, and sortable headers showed no indicator until they were already sorted; both replaced with inline SVG chevrons in a new `src/components/ui/icons.tsx`, rather than adding `lucide-react` for three glyphs. Bundle unchanged at 58.61 KB delta.
- `react-mui` (5175): the Status, Priority and Assignee labels printed on top of their own placeholder text. `InputLabel` only shrinks on focus or a non-empty value, and with `displayEmpty` a placeholder still counts as empty, so the label never floated. Fixed with `shrink` on those three labels, matching what the date fields in the same form already did. Bundle unchanged at 79.74 KB delta.
- `react-chakra` (5176): the provider and style engine were mounted correctly, which the survey had guessed might be the cause and was not. Chakra's `Field.Root` and `Fieldset.Root` recipes set `width: 100%`, and the form capped fields only with `minW`, a floor rather than a ceiling, so every field's flex-basis resolved to the full row and wrapped one per line. That also made the native multi-selects render nearly 1400px wide, which is what read as unstyled. Fixed with explicit `flex` and `width="auto"` per field, plus a `Container` on the screen. Bundle unchanged at 97.72 KB delta.
- `react-antd` (5177): the native date inputs were styled to antd's own seed tokens (32px control height, 6px radius, `#d9d9d9` border, matching font) so they sit with the Selects, and the From and To labels moved inline so the group stops being a line taller than its neighbours. `DatePicker` was deliberately not adopted, since it costs about 37 KB gzip on a build already over budget. Bundle unchanged at 233.45 KB delta, still over.
- `vue-vuetify` (5178): `main.ts` never imported `vuetify/styles`. `vite-plugin-vuetify`'s auto-import resolves component styles but is not a substitute for the base stylesheet, so `VField`'s outlined-variant CSS never loaded and empty selects showed their label struck across the border with no caret. Fixed by importing it and switching to the `mdi-svg` iconset, which needs no font. Sortable headers were uppercase only because their label sits in a `v-btn`, whose recipe forces `text-transform: uppercase`; overridden with a scoped rule. Added a `v-container`. **This moved a recorded number: 120.17 to 153.08 KB total, 95.96 to 128.87 KB delta.** The old figure measured a build that was never loading the library's own CSS, so it understated Vuetify by about 33 KB. The new one is the honest number and it is still inside budget.
- `vue-primevue` (5179): PrimeVue's `options.darkModeSelector` defaults to `'system'`, so on a machine with a dark OS preference the preset's dark tokens matched and every themed control flipped, while the hand-written light colors in `styles.css` stayed put. That same switch put near-white text on the badges' fixed light-grey pills, which is where the unreadable contrast came from. Fixed with `darkModeSelector: false`, threaded through both `main.ts` and the test adapter so production and Jest configure PrimeVue identically. The trimmed preset and the dropped `primeicons` font were left alone. Bundle unchanged at 150.17 KB delta.
- `vue-quasar` (5180): no Material Icons font was ever loaded, so all six `QSelect`s printed the ligature name `arrow_drop_down` as text, and that 16-character string overflowing its icon slot was also what made the fields appear to overlap. Fixed by passing the caret as an SVG path string, which `QIcon`'s `isSvgPath` branch renders inline, so no font was added. Created between had the same fieldset legend bug as `react-headless` and got the same treatment, minus the extra `<label>` wrappers, which would have reintroduced an axe violation this build already fixed once. Bundle unchanged at 91.63 KB delta.

Two cross-build inconsistencies are deliberately **not** on the fix list. Badge labels are capitalized in `react-headless`, `react-shadcn` and `react-chakra` but lowercase in `react-mui`, `react-antd`, `vue-vuetify` and `vue-quasar`, and only `react-shadcn` renders a visible page heading, though the spec never asks for one. Both are library defaults showing through, which is exactly what the comparison is built to measure, so they stay as recorded findings for the write-up. Do not normalize them.

## 8. Renaming "bakeoff" to "ui library comparison"

The owner chose `ui-library-comparison` as the new name. This is one job covering the repo and the demo resume, because the resume is where the project is described publicly and the two names have to agree. As of 2026-09-03 nothing below has been done.

Size it as a medium job: 338 occurrences across 142 files, and it touches the `@uilc/*` package names that every build imports, so it cannot be done as a blind find and replace and left unverified.

**Do it in one pass, not incrementally.** A half-renamed workspace does not install, and a build whose dependency names no longer resolve reports every module as missing, which looks like a much worse problem than it is.

The naming, so it is decided once rather than per file:

- Repo folder: `ui-library-comparison` becomes `ui-library-comparison`.
- Root package name: `ui-library-comparison` becomes `ui-library-comparison`.
- Package scope: `@uilc/*` becomes `@uilc/*`, giving `@uilc/fixture`, `@uilc/criteria`, `@uilc/harness`, `@uilc/baseline-react`, `@uilc/baseline-vue`, and `@uilc/<build>` for all eight builds. A short scope keeps the many import lines readable; `@ui-library-comparison/*` would be correct and unpleasant to type.
- Per build declaration file: `comparison.json` becomes `comparison.json`, in all eight builds and in `templates/common/comparison.json.tmpl`.
- The `BakeoffAdapter` and `BuildResult` types in `packages/harness`: `BakeoffAdapter` becomes `ComparisonAdapter`. `BuildResult` already has no "bakeoff" in it and stays.
- The two agent definitions, `.claude/agents/comparison-builder.md` and `.claude/agents/comparison-owner.md`, get renamed and their frontmatter `name` fields updated to match, or nobody can dispatch them by name.
- Prose in `README.md`, `CLAUDE.md`, `spec/screen-spec.md`, this file, and the eight build `README.md`s. In prose, write "the comparison", not "the bake-off".

Order of operations:

1. Stop all eight dev servers first. On Windows a directory cannot be renamed while any process has it as a working directory, and that includes an editor or shell sitting inside it, so the folder rename cannot be done by an agent whose own working directory is the folder. Do the folder rename from outside, or do it last.
2. Rename the package names and the scope across `package.json` files, then the `workspace:*` dependency entries that refer to them.
3. Rename the identifiers and the file names, `comparison.json` to `comparison.json` in all eight builds plus the template, and update `scripts/measure.ts`, which reads that filename.
4. Run `pnpm install`. The lockfile will rewrite, since package names are keys in it. That is expected and its diff will be large.
5. Update the prose everywhere, including this file.
6. Update the demo resume at `../demo-resume/demo-resume.md`, line 148, currently `### Component library bake-off, public write-up`. Change the heading and any body prose that says "bake-off", keeping the user's writing rules. Do not add claims: that entry already describes a screen reader walkthrough, a public write-up and public demos, none of which exist yet, and a rename is not the moment to quietly fix that. See the note in section 6.

Verification, and none of it is optional, since a rename that breaks the suite silently invalidates all eight results:

- `pnpm install` completes with no unresolved workspace dependency.
- `pnpm typecheck` passes, plus `npx tsc --noEmit -p tsconfig.json` inside each of the eight builds.
- `pnpm build` builds all ten apps.
- `pnpm -r --filter "./builds/*" test` passes all 18 criteria in all eight builds. Budget hours for this: `react-antd` alone takes around 560 seconds, since axe-core runs 2 to 4 minutes per test against its DOM.
- `pnpm fixture:check` passes.
- Grep for `bakeoff` case-insensitively across the repo, excluding `node_modules` and `.git`, and confirm the only hits left are in git history.
- Confirm `results/*.json` still holds the same eight bundle numbers afterwards. A rename must not move them. If one moved, something else changed too and needs finding.
